# escape: сайт-обманка fake-webapp за nginx в Docker

[English](README.en.md) | Русский

Инструмент разворачивает на сервере Docker-стек: контейнер `nginx` принимает HTTPS на 443 и отдаёт сайт-обманку `fakeapp`. Это правдоподобная страница входа в веб-сервис (Go, исходники в `fake-webapp/`). Её видят обычные посетители и активные зонды, которые заходят на ваш домен без ключа VPN.

nginx публикует порты 80 и 443 хоста, получает сертификат Let's Encrypt для вашего домена (certbot, метод webroot) и сам продлевает его. На 443 сначала стоит TLS-фронт (модуль stream): он смотрит на имя сервера (SNI) и, не расшифровывая, передаёт соединение HTTPS-серверу nginx или, для имён, которые заявило расширение, его сервису (см. [«nginx в контейнере»](#nginx-в-контейнере)). `fakeapp` наружу не публикуется: он доступен только внутри сети compose как `http://fakeapp:<порт>`. Дополнительные сервисы (расширения) подключаются к этому стеку отдельными файлами и добавляют свои `location` в nginx (см. [«Расширения»](#расширения)). Базовая установка **не трогает** Xray, 3X-UI и файрвол; это делает только необязательное расширение [`xray-3xui`](#панель-3x-ui-xray-xray-3xui), если его выбрать.

## Требования

- Ubuntu 22.04+ или Debian 12+, права root (`sudo`).
- Docker с плагином compose v2.20+. Если Docker уже стоит (например, на нём работает 3X-UI), используется он, его настройки не меняются. Если Docker нет, ставится Docker CE из `download.docker.com`. Если нет только плагина compose, ставится плагин.
- `python3`, `curl`, `iproute2`, `openssl` (ставятся автоматически, если их нет).
- Свободные порты 80 и 443 (nginx на хосте или Xray на 443 нужно остановить или перенести) и DNS-запись A/AAAA вашего домена, указывающая на этот сервер: без неё Let's Encrypt сертификат не выдаст. Сервер: 1 CPU и 1 ГБ памяти достаточно.

## Установка

```bash
curl -fsSL https://raw.githubusercontent.com/dv-proj/escape/main/install.sh | sudo bash -s -- install
```

Скрипт скачивает репозиторий архивом (`curl`, git не нужен) во временный каталог, запускает `install.sh` оттуда и удаляет временный каталог при выходе. Вопросы задаются в терминале: сначала язык, затем [каталог установки](#каталог-установки) (по умолчанию `/opt/escape`), затем остальное. `install` копирует проект в каталог установки и продолжает работу из установленной копии (`/opt/escape/install.sh`); от загрузки ничего больше не остаётся. Свой язык и флаги передаются после `--`, например `... | sudo bash -s -- --lang ru --dir /srv/escape install`.

Загрузка настраивается переменными окружения (значения по умолчанию в скобках; передавайте через `sudo -E` или `sudo VAR=...`): `ESCAPE_REPO_URL` (`https://codeload.github.com/dv-proj/escape`; архив: `<ESCAPE_REPO_URL>/tar.gz/<ref>`), `ESCAPE_BRANCH` (`main`; ветка, тег или хеш коммита; `FAKEAPP_BRANCH` — устаревший псевдоним). Повторный запуск той же команды — это **обновление**: код в каталоге установки заменяется скачанным, `.env` и `data/` сохраняются (см. [Обновление](#обновление)).

Другой способ: склонировать репозиторий самому и выполнить из него `sudo ./install.sh install`. Клон остаётся только источником: его файлы копирует тот же шаг, а сам клон каталогом установки не бывает (такой выбор отклоняется).

### Язык сообщений

Первый вопрос `install` (и `extensions --with`, если запустить их одни в терминале): `Language / Язык: 1 - English, 2 - Russian [1]`, по умолчанию английский. Выбор можно задать заранее: флагом `--lang en|ru` или переменной окружения `FAKEAPP_LANG`; тогда вопроса нет. Выбор сохраняется в `.env` (ключ `FAKEAPP_LANG`) и при следующих запусках применяется молча (включая `status`, `logs` и остальные команды); флаг и переменная окружения важнее значения из `.env` и при `install` обновляют его. Неизвестное значение (не `en` и не `ru`) попадает в список проблем фазы проверки. Без терминала и без указания языка используется английский. Команды, флаги, имена переменных, пути и вывод Docker, apt и certbot не переводятся.

Установка идёт тремя фазами, одинаково для основной части и для каждого расширения:

1. **Сбор.** Сначала выбор языка, затем каталог установки, затем все вопросы сразу: домен, e-mail для Let's Encrypt, название, описание и ключевые слова сайта, затем меню дополнительных функций (расширений) и вопросы самих расширений (например, исходящий интерфейс). Переменные окружения и флаги заменяют вопросы; без терминала вопросов нет. Ничего не устанавливается и не меняется.
2. **Проверка.** Все значения проверяются вместе до развёртывания: каталог установки (он проверяется, как только известен, и проект копируется только после этого), имя домена, свободные порты 80/443, файлы проекта, исходящий интерфейс и другие проверки расширений. DNS домена проверяется предупреждением (указывает ли он на этот сервер). Все найденные проблемы выводятся списком сразу; если среди них есть серьёзные, установка прекращается до начала развёртывания.
3. **Развёртывание.** Только теперь ставятся пакеты и Docker, пишутся `.env` и конфигурация, собирается и запускается стек, выпускается сертификат, применяются расширения. Вопросов здесь больше нет.

Меню расширений показывается после вопросов основной части. Без меню: `--with id1,id2` (или `--with all`), либо переменная `FAKEAPP_EXTENSIONS` с тем же значением; отдельно от основной установки расширения ставит `./install.sh extensions --with id`. Список: `./install.sh extensions`. Как добавить своё расширение: [extensions.d/README.md](extensions.d/README.md).

Скрипт задаёт только эти вопросы:

| Вопрос | Ключ `.env` | По умолчанию |
|---|---|---|
| Язык: `Language / Язык: 1 - English, 2 - Russian [1]` | `FAKEAPP_LANG` | `en` |
| Каталог установки (`--dir`, `ESCAPE_DIR`; в `.env` не хранится) | нет | `/opt/escape` или каталог существующей установки (файл-указатель) |
| DNS-имя сайта, например `app.example.com` (обязательно) | `DOMAIN` | нет: без него установка не идёт дальше |
| E-mail для Let's Encrypt (необязательно) | `LE_EMAIL` | пусто: регистрация без e-mail |
| Название сайта | `APP_NAME` | случайное правдоподобное |
| Описание сайта | `APP_DESCRIPTION` | случайное, в тон названию |
| Ключевые слова | `APP_KEYWORDS` | случайные, в тон названию |
| Часовой пояс | `TZ` | часовой пояс хоста |

- **`DOMAIN`** задаёт `server_name` nginx, домен сертификата и теги `canonical` и `og:url` (`https://<DOMAIN>`). Если в существующем `.env` его нет или он пуст, скрипт спросит при следующем запуске.
- Порты nginx (`NGINX_HTTP_PORT`, `NGINX_HTTPS_PORT`, по умолчанию 80 и 443), `LE_STAGING` (`1`: тестовый CA Let's Encrypt, сертификат не доверенный, без лимитов) и порт приложения внутри сети (`FAKEAPP_PORT`, 8080) не спрашиваются: при необходимости задайте их переменными окружения при первом запуске или правьте `.env`. Скрипт проверяет, что порты nginx свободны, и называет программу, которая их занимает. Порт 80 нужен Let's Encrypt для проверки домена: при другом `NGINX_HTTP_PORT` пробросьте 80 на него.

Остальные параметры генерируются случайно: `PAGE_SEED` (вариант оформления), `RANDOM_DATA_SUFFIX`, лимиты запросов (`RATE_LIMIT_RPS`, `RATE_LIMIT_BURST`, `RATE_LIMIT_GLOBAL_RPS`) и задержки входа (`LOGIN_DELAY_MIN_MS`, `LOGIN_DELAY_MAX_MS`). Без терминала вопросы не задаются: берутся значения по умолчанию или переменные окружения с теми же именами, например `DOMAIN=app.example.com LE_EMAIL=me@example.com sudo -E ./install.sh install`. Без `DOMAIN` установка без терминала завершится ошибкой.

Что делает `install` после проверок: создаёт временный самоподписанный сертификат (чтобы nginx стартовал сразу), собирает и запускает стек, затем запрашивает настоящий сертификат одноразовым контейнером certbot и подставляет его в nginx. Если сертификат получить не удалось (DNS указывает не сюда, порт 80 недоступен из интернета, лимиты Let's Encrypt), скрипт печатает причину и подсказку, остальная установка не прерывается, nginx работает с самоподписанным сертификатом. Исправьте причину и выполните `sudo ./install.sh renew` (или повторите `install`). Сертификаты хранятся в `data/letsencrypt/`. Продление: systemd-таймер `escape-certbot-renew.timer` (дважды в сутки запускает `<каталог установки>/install.sh renew`: `certbot renew` и перезагрузка nginx); если systemd не запущен, ставится запись в `/etc/cron.d/escape-certbot`.

Повторный `install` заново копирует проект в каталог установки, пересобирает и перезапускает стек и вопросов не задаёт (кроме языка, если он ещё не выбран, и каталога, если он неизвестен). Значения в `.env` он не меняет, только дописывает новые ключи из `.env.example` (и записывает выбранный язык). Существующие `login.html` и `favicon.ico` тоже не трогает.

## Каталог установки

Проект никогда не запускается из git-клона. `install` берёт исходники (клон или распакованную загрузку) и **копирует из них белый список файлов** в каталог установки. В нём лежит только то, что нужно для работы системы, всё, что создаёт установка, живёт в нём же, а всё, что снаружи, перечислено ниже.

**Выбор каталога.** Второй вопрос `install` (после языка): по умолчанию `/opt/escape`; `--dir PATH` или `ESCAPE_DIR` задают его без вопроса (`FAKEAPP_DIR` — устаревший псевдоним). Если установка уже есть, по умолчанию предлагается её каталог (из файла-указателя, см. ниже). Путь проверяется первым, до любого копирования:

- абсолютный, только буквы, цифры и `. _ / + @ : -` (без пробелов); не `/` и не системный каталог (`/usr`, `/etc`, `/var`, `/home`, `/opt`, `/tmp` сами по себе, домашний каталог пользователя, ...);
- он может ещё не существовать (ближайший существующий родитель должен быть доступен на запись: запускайте от root), быть пустым (или содержать только `.env` и `data/`, скопированные из старой установки) или быть **существующей установкой этого проекта** (в нём есть файл-маркер `.escape-install`): тогда код обновляется, а `.env` и `data/` сохраняются;
- непустой каталог, который не является нашей установкой, — проблема с подсказкой: старая схема (git-клон вроде `/opt/fakeapp`) никогда не переиспользуется и не затрагивается, см. [Перенос со старой схемы](#перенос-со-старой-схемы); клон, из которого запущен скрипт, тоже не может быть каталогом установки.

**Состав каталога установки** (по умолчанию `/opt/escape`):

```text
/opt/escape/
├── .escape-install        маркер: каталог — установка проекта
├── .env                   настройки (режим 600); обновление его не перезаписывает
├── .env.example           шаблон (новые ключи при обновлении дописываются в .env)
├── install.sh             точка входа всех команд
├── docker-compose.yml     основной compose-файл (проект "escape")
├── README.md, README.en.md
├── lib/                   модули install.sh, lib/lang/ (сообщения)
├── nginx/                 docker-compose.yml (nginx, certbot), default.conf.template
├── fake-webapp/           контекст сборки приложения-обманки: Dockerfile, .dockerignore, go.mod,
│                          *.go, docker-compose.yml, gen/login.py, gen/favicon.py (без тестов)
├── extensions.d/          расширения: <NN>-<id>.sh, <id>/ (их скрипты и lang/)
├── scripts/               самостоятельные tgproxy-*.sh (создаёт расширение telegram-web-proxy)
└── data/                  ВСЕ данные времени работы (bind-монтирования; именованных томов Docker нет)
    ├── fakeapp/           login.html, favicon.ico, ваши файлы (в контейнере только для чтения)
    ├── nginx/             conf.d/, locations.d/, servers.d/, selfsigned/, webroot/, extra-certs.list
    ├── letsencrypt/       сертификаты, аккаунт ACME, конфиги продления
    ├── extensions.compose.yml   генерируется: compose-файлы установленных расширений
    └── telegram-web-proxy/      расширение: state.env, telemt/config.toml, docker-compose.yml,
                                 nginx-*.conf, telemt-image.tar
```

Здесь нет `.git*`, `.github`, `tests/`, файлов редакторов и `CLAUDE.md`/`AGENTS.md`. Всё в `data/` — ваше: `install` его не удаляет и не перезаписывает. Единственное исключение из правила «всё в каталоге установки» — `FAKEAPP_DATA_DIR` в `.env`, если вы задали его сами. Проект compose называется `escape` (контейнеры `escape-nginx-1`, `escape-fakeapp-1`, сеть `escape_default`), поэтому не пересекается со старым проектом `fakeapp`.

**Вне каталога установки** (только то, что не может лежать внутри; `remove --purge` удаляет всё перечисленное):

| Что | Где |
|---|---|
| указатель на установку | `/etc/escape/install-dir` (путь к каталогу; пишет `install`, поэтому команды работают из любого каталога) |
| таймер продления сертификатов | `/etc/systemd/system/escape-certbot-renew.service` и `.timer`, либо `/etc/cron.d/escape-certbot`, если systemd не запущен |
| outway Telegram web proxy (расширение) | `/etc/systemd/system/telegram-web-proxy-outway.service`, `-outway-check.service`, `-outway.timer`; `/etc/sysctl.d/90-telegram-web-proxy.conf`; записи `ip rule` / `ip -6 rule`, таблица маршрутизации 7791, цепочки `TGPROXY-OUTWAY` (iptables/ip6tables или таблица nft `tgproxy_outway`) |
| Docker | образы (`nginx`, `certbot`, `telemt`, собранный `fakeapp`), контейнеры и сети под управлением Docker; сам Docker и пакеты apt не удаляются никогда |

**Запуск команд.** Команды (`start`, `stop`, `status`, `logs`, `renew`, `remove`, `info`, `extensions`) всегда выполняют установленную копию: `sudo /opt/escape/install.sh status`. При запуске из другого каталога (или из клона) `install.sh` находит установку по `--dir`, `ESCAPE_DIR` или `/etc/escape/install-dir` и выполняет установленный `install.sh` с теми же аргументами; если ничего из этого нет, он останавливается с подсказкой. Таймер продления и юниты расширения указывают на установленную копию и её `scripts/`. Если на хосте несколько установок, передавайте `--dir` явно (файл-указатель хранит последнюю).

### Обновление

Выполните ту же команду-однострочник ещё раз (или `sudo ./install.sh install` из свежего клона / загрузки):

1. проект копируется из новых исходников в каталог установки (белый список файлов; файлы, которые есть в `lib/`, `nginx/`, `extensions.d/`, `fake-webapp/` каталога установки, но уже не существуют в исходниках, удаляются, поэтому убранные модули исчезают);
2. `.env`, `data/`, `scripts/` и всё остальное, что вы там храните, не затрагиваются; новые ключи `.env.example` дописываются в `.env`;
3. стек пересобирается и перезапускается, таймер продления и скрипты расширений обновляются.

Не правьте скопированный код в каталоге установки: следующее обновление его перезапишет. Свои изменения вносите в репозиторий с исходниками.

### Перенос со старой схемы

Прежние версии запускались из git-клона в `/opt/fakeapp` (данные в его `data/`, скрипты расширения в `/opt/fakeapp-tgproxy` или `~пользователь/telegram-web-proxy`, таймер `fakeapp-certbot-renew`). Новая установка его не определяет и не меняет. Чтобы перенести:

1. Остановите старую установку в её каталоге. Если используется Telegram web proxy, сначала выполните его `tgproxy-remove.sh` **без** `--purge` (он удалит контейнер, правила и юниты outway и маршрут nginx, но оставит `data/telegram-web-proxy/` с секретами, поэтому ссылка не изменится). Затем `sudo ./install.sh remove` (тоже без `--purge`).
2. Скопируйте настройки и данные в новый каталог: `sudo mkdir -p /opt/escape && sudo cp -a /opt/fakeapp/.env /opt/fakeapp/data /opt/escape/`. Каталог, в котором лежат только `.env` и `data/`, принимается как каталог установки.
3. `sudo ./install.sh install` из свежего клона или однострочник: код копируется в `/opt/escape`, `.env`, файлы сайта и сертификаты переиспользуются, стек поднимается как новый проект `escape`. Порты 80/443 после шага 1 свободны.
4. Telegram web proxy: выберите его в меню (или `--with telegram-web-proxy`) снова: он найдёт сохранённое состояние, перепишет свои пути (`scripts/` в новом каталоге, проект `escape`) и установит ту же ссылку.
5. Когда всё работает, удалите старый клон и, если остался, старый таймер: `sudo systemctl disable --now fakeapp-certbot-renew.timer; sudo rm -f /etc/systemd/system/fakeapp-certbot-renew.* /etc/cron.d/fakeapp-certbot`; старый каталог скриптов (`/opt/fakeapp-tgproxy` или `~пользователь/telegram-web-proxy`) удаляет `tgproxy-remove.sh --purge` или вы вручную.

Автоматического переноса нет.

## Команды

Общий вид: `install.sh [флаги] <команда>`. Без команды выводится справка (код возврата 2). В примерах ниже написано `./install.sh`: запускайте его из каталога установки (`cd /opt/escape`) или по полному пути; из любого другого места установка находится по `/etc/escape/install-dir` (см. [Каталог установки](#каталог-установки)).

| Команда | Действие |
|---|---|
| `sudo ./install.sh install` | установка или обновление (см. выше); из клона / загрузки сначала копирует проект в каталог установки |
| `./install.sh start` / `stop` / `restart` | запуск, остановка, перезапуск стека (`start` и `restart` заново генерируют конфигурацию nginx) |
| `./install.sh info` | повторно вывести итоговые данные: путь random-data fake-app и строку подключения web-proxy (они же печатаются отдельным блоком «Итоговые данные» в конце `install`) |
| `./install.sh status` | состояние контейнеров, сертификат, таймер продления и проверка `https://<DOMAIN>/` на этом сервере (`curl --resolve` на `127.0.0.1`) |
| `./install.sh logs` | журналы контейнеров (выход: Ctrl+C) |
| `sudo ./install.sh renew` | продлить сертификаты и перечитать конфигурацию nginx; если сертификата ещё нет, запросить его |
| `./install.sh extensions` | список расширений; с `--with id,...` (root) ставит их, как при `install` |
| `sudo ./install.sh remove [--purge] [-y]` | удалить контейнеры, образы и таймер продления; каталог установки, `.env` и `data/` остаются. С `--purge` удаляется всё, что создала установка: системные файлы расширений, данные (включая сертификаты), весь каталог установки и `/etc/escape/install-dir`. Docker остаётся |

Для `start`, `stop`, `restart`, `status` и `logs` нужен доступ к Docker: root, `sudo` или группа `docker`. Справка: `./install.sh --help` (или `-h`, `help`); на выбранном языке: `./install.sh --lang ru --help`.

|---|---|

### Переменные окружения

Используются при создании `.env` (вместо вопросов; передавайте через `sudo -E` или `sudo VAR=...`): `DOMAIN`, `LE_EMAIL`, `LE_STAGING`, `NGINX_HTTP_PORT`, `NGINX_HTTPS_PORT`, `FAKEAPP_PORT`, `APP_NAME`, `APP_DESCRIPTION`, `APP_KEYWORDS`. Незаданные `APP_*` генерируются случайно. `TZ` из окружения не читается: берётся часовой пояс хоста (или значение, введённое в ответ на вопрос). Остальные: `FAKEAPP_LANG` (язык), `FAKEAPP_EXTENSIONS` (расширения без меню), `ESCAPE_DIR` (каталог установки; `FAKEAPP_DIR` — устаревший псевдоним), `ESCAPE_REPO_URL`, `ESCAPE_BRANCH` (загрузка через `curl | bash`; `FAKEAPP_BRANCH` — устаревший псевдоним), `NO_COLOR` (отключить цвет). Переменные расширений описаны в их разделах (`TGPROXY_*`, `XRAY_*`).

## nginx в контейнере

- Образ: официальный `nginx:stable-alpine`, один контейнер, журнал доступа отключён (`access_log off`).
- Главный конфиг `nginx/nginx.conf` монтируется в контейнер вместо стандартного: в нём блок `http` (подключает `conf.d/*.conf`) и блок `stream` (подключает `conf.d/*.stream`). Конфигурации `data/nginx/conf.d/default.conf` (HTTPS-сервер) и `data/nginx/conf.d/front.stream` (TLS-фронт) генерирует скрипт из шаблонов `nginx/default.conf.template` и `nginx/stream.conf.template`: вручную их не правьте, изменения затираются при `install`, `start`, `restart` и `renew`. Подстановки берутся из `.env` (`DOMAIN`, `FAKEAPP_PORT`, `NGINX_HTTPS_PORT`).
- Порт 80: путь `/.well-known/acme-challenge/` отдаёт webroot certbot'а, всё остальное получает редирект 301 на `https://<DOMAIN>/`.
- Порт 443 хоста (`NGINX_HTTPS_PORT`) — это **TLS-фронт** (контейнерный порт 4443, `stream` с `ssl_preread`): он читает SNI из ClientHello и, не завершая TLS, отправляет соединение дальше. Имена, которые заявили расширения (`data/nginx/stream.d/<id>.map`, функция `ext_nginx_stream_put`), уходят в сервис расширения; всё остальное (`DOMAIN`, имена расширений из `servers.d`, соединения без SNI) уходит в HTTPS-сервер того же nginx (`127.0.0.1:443` внутри контейнера, на хост не публикуется). Каждое соединение фронт передаёт с заголовком PROXY protocol v1, поэтому получатель знает настоящий адрес клиента. Без расширений фронт прозрачен: всё идёт в HTTPS-сервер.
- HTTPS-сервер (`listen 443 ssl proxy_protocol`): `http2`, TLS 1.2 и 1.3, `server_name <DOMAIN>`. Адрес клиента он берёт из заголовка PROXY (`real_ip_header proxy_protocol`, доверие только к `127.0.0.1`, то есть к фронту; расширения могут добавить доверенного отправителя через `set_real_ip_from` на уровне http в `servers.d`), поэтому `$remote_addr`, `X-Real-IP` и `X-Forwarded-For` — это настоящий адрес клиента, как и раньше. Блок `location /` проксирует в `http://fakeapp:<порт>`, при этом `X-Real-IP` и `X-Forwarded-For` перезаписываются адресом клиента (`$remote_addr`), передаются `X-Forwarded-Proto` и `Host`. Приложение верит `X-Real-IP`, поэтому его порт нигде не публикуется. Блоки `server` расширений с `listen 443 ssl` (например, отдельное имя Telegram web proxy) делят этот же сокет и тоже получают адрес из PROXY; менять их не нужно.
- Перед `location /` в блок 443 подключается `include /etc/nginx/locations.d/*.conf;`: каталог `data/nginx/locations.d/` смонтирован в контейнер, расширения кладут туда по одному `.conf` с блоком `location`.
- На уровне http подключается `include /etc/nginx/servers.d/*.conf;` (каталог `data/nginx/servers.d/`, тоже смонтирован): расширение со своим DNS-именем кладёт туда свои блоки `server` целиком (`ext_nginx_server_put`) со своим сертификатом Let's Encrypt (`ext_cert_request`). Зарегистрированные имена перечислены в `data/nginx/extra-certs.list`; `renew` (таймер) продлевает их вместе с сертификатом `DOMAIN` и выпускает ещё отсутствующие. Установку, сделанную до появления `servers.d`, переводят на новую схему `start`/`restart`/`install` или первое расширение, которому она нужна (конфиг собирается заново, контейнер nginx однократно пересоздаётся, сайт недоступен несколько секунд).
- Переход на TLS-фронт происходит так же автоматически: `install` (обновление), `start`, `restart` собирают оба конфига заново и пересоздают контейнер nginx с новыми портами и монтированиями; если работающий контейнер ещё старый (443 хоста ведёт прямо в HTTPS-сервер, нет `stream.d`), его однократно пересоздаёт и любая перезагрузка конфига (`renew`, функции `ext_nginx_*`), чтобы сайт не остался без фронта. Сертификаты, продление, ACME на порту 80, `status` и маршруты Telegram web proxy (и `location`, и отдельное имя) работают как прежде.
- Пока настоящего сертификата нет, используется временный самоподписанный (`data/nginx/selfsigned/`). Браузеры его не принимают, это нормально до выдачи Let's Encrypt.
- Xray или 3X-UI на этом же сервере: 443 теперь занимает nginx, поэтому перенесите их на другой порт или подключите расширением: HTTP-сервис через `location`, TLS-сервис с собственным SNI (например, Xray REALITY) через маршрут TLS-фронта (`ext_nginx_stream_put`). Готовое расширение для панели 3x-ui с Xray: [`xray-3xui`](#панель-3x-ui-xray-xray-3xui).

Проверка:

```bash
./install.sh status
curl -sI https://<DOMAIN>/ | head -n1
```

Ожидается `HTTP/2 200`. Любой несуществующий путь отвечает редиректом 302 на `/`. Ваш реальный IP должен появиться в журнале приложения (`./install.sh logs`); если там у всех адрес `172.x.x.x`, значит nginx не передаёт `X-Real-IP`.

## Расширения

Дополнительные функции ставятся из `extensions.d/` и не правят общие файлы стека: расширение добавляет свой compose-файл в `data/extensions.compose.yml` (`ext_register_compose`) и свой `location` в `data/nginx/locations.d/<id>.conf` (`ext_nginx_location_put`), для собственного DNS-имени: блоки `server` целиком в `data/nginx/servers.d/<id>.conf` (`ext_nginx_server_put`) и сертификат этого имени (`ext_cert_request`), а для TLS-сервиса со своим SNI на 443: маршрут TLS-фронта в `data/nginx/stream.d/<id>.map` (`ext_nginx_stream_put`). Подробности, сигнатуры функций и пример: [extensions.d/README.md](extensions.d/README.md).

Расширение регистрируется вызовом `register_extension ID "Название" ФУНКЦИЯ` и участвует в трёх фазах установки через необязательные хуки: `ext_<id>_collect` (все вопросы, ничего не меняет), `ext_<id>_validate` (проверки только на чтение, проблемы через `problem`) и функция развёртывания (без вопросов); в имени хука `-` из `<id>` заменяется на `_`. Функции-помощники: `ext_register_compose`, `ext_unregister_compose`, `ext_nginx_location_put`, `ext_nginx_location_rm`, `ext_nginx_server_put`, `ext_nginx_server_rm`, `ext_nginx_stream_put`, `ext_nginx_stream_rm`, `ext_cert_request`, `ext_cert_release`, `ext_cert_paths`, `check_domain_dns`, `ext_domain`, `env_value`, `problem`, `ext_compose`, а для сообщений `t` и `ext_load_lang`. Тексты расширения хранятся в `extensions.d/<id>/lang/en.sh` и `ru.sh`.

### Telegram web proxy (`telegram-web-proxy`)

Расширение `extensions.d/50-telegram-web-proxy.sh` поднимает рядом с сайтом-обманкой веб-прокси Telegram на базе [TELEMT](https://github.com/telemt/telemt) (образ `ghcr.io/telemt/telemt:3.5.17`, режим WEB). Клиент открывает ссылку вида `tg://webproxy?server=<имя прокси>%2F<секретный путь>&secret=...` и ходит на `https://<имя прокси>/<секретный путь>/` по обычному HTTPS на 443. nginx отдаёт TELEMT **только** этот путь (`location ^~ /<путь>/` и точный `location = /<путь>`), всё остальное по-прежнему уходит в `fakeapp`; неверные запросы внутри секретного пути TELEMT тоже перенаправляет в обманку (`fakeapp`). Контейнер `telemt` не публикует порты: nginx достучится до него по сети compose (`telemt:18080`), `telemt` до обманки по `http://fakeapp:<порт>`.

**Имя прокси.** Установка спрашивает DNS-имя прокси (`TGPROXY_DOMAIN`), то есть хост в ссылке. Enter оставляет имя сайта (`DOMAIN`, как в прежних версиях): тогда секретный путь подключается `location`'ом в server 443 сайта (`data/nginx/locations.d/telegram-web-proxy.conf`). Отдельному имени (например, сайт на `app.example.org`, прокси на `p.example.org`) нужна своя A/AAAA-запись на этот сервер (если имя ещё не разрешается, это только предупреждение, как для `DOMAIN`), и оно получает:

- свои блоки `server` в `data/nginx/servers.d/telegram-web-proxy.conf` (`ext_nginx_server_put`): порт 80 отвечает на запросы ACME и перенаправляет на HTTPS; порт 443 отдаёт секретный путь TELEMT, а **все остальные пути** (и `/`) обманке `fakeapp` с теми же заголовками, что `location /` сайта; на самом сайте (`DOMAIN`) секретного пути больше нет;
- свой сертификат Let's Encrypt (`ext_cert_request`, certbot webroot, продлевается таймером вместе с сертификатом сайта). Пока его нет, nginx отдаёт для этого имени временный самоподписанный сертификат, который Telegram Desktop не принимает: ошибка выпуска — предупреждение с подсказками, установка продолжается, повторить можно через `sudo ./install.sh renew` (или таймер, или `tgproxy-config.sh cert`).

Имя хранится в `state.env` (`TGPROXY_DOMAIN`). Установка, сделанная до появления этого вопроса (в `state.env` нет `TGPROXY_DOMAIN`), продолжает работать на `DOMAIN`; повторный запуск предлагает «обновить», и обновление спрашивает имя (Enter оставляет `DOMAIN`). Смена имени меняет ссылку.

**Требования.** Стек установлен и запущен (`DOMAIN` берётся из `.env`, повторно не спрашивается); `NGINX_HTTPS_PORT=443` (Telegram Desktop принимает только 443); `iproute2`, `openssl`, `python3`, `iptables` или `nft` на хосте; доступ к `ghcr.io` при первой установке. Клиент: **Telegram Desktop 7.1 или новее** (тип прокси WEB). Мобильные клиенты не проверялись. Ресурсы: контейнер ограничен `128m` памяти (`TGPROXY_MEM_LIMIT`), в простое занимает десятки МБ; для сервера 1 CPU и 1 ГБ запас большой.

**Установка.** Пункт меню «Telegram web proxy» (после вопросов основной части) в конце `install`, либо без меню:

```bash
TGPROXY_OUTWAY=eth0 sudo -E ./install.sh extensions --with telegram-web-proxy
```

Установка генерирует случайный секретный путь (20 символов) и секрет пользователя (32 hex), пишет `data/telegram-web-proxy/config.toml` (режим 600, владелец uid контейнера) и `state.env` (режим 600), подключает compose-файл (`ext_register_compose`) и `location` (`ext_nginx_location_put`; при отдельном имени прокси вместо него блоки `server` и сертификат), настраивает outway, сохраняет образ командой `docker save` в `data/telegram-web-proxy/telemt-image.tar` (`TGPROXY_SAVE_IMAGE=0` отключает) и в конце печатает ссылку `tg://webproxy?...`, интерфейс outway и предупреждения. Ссылку берёт из журнала TELEMT (он печатает её при старте); если в журнале её уже нет, вычисляет по документированному формату.

Повторный запуск расширения на установленной системе открывает меню: обновить (скачать образ, пересобрать конфиг, сохранить секреты, если их не меняют), удалить, показать ссылку, сменить outway, сменить секретный путь/секрет, статус. Без терминала действие задаётся переменными окружения (передавайте их через `sudo -E` или `sudo VAR=...`):

| Переменная | Значение |
|---|---|
| `TGPROXY_ACTION` | `install`, `update`, `remove`, `link`, `outway`, `rotate`, `status`. По умолчанию: `install`, а на установленной системе `update` |
| `TGPROXY_DOMAIN` | имя прокси (хост ссылки) при `install` и `update`; по умолчанию текущее, а если его нет, `DOMAIN` |
| `TGPROXY_OUTWAY` | **имя** интерфейса outway (`eth0`, `wg0`, ...; номер из списка принимает только вопрос в терминале) или `auto` (интерфейс маршрута по умолчанию, IPv4, а если его нет, IPv6); обязательна при установке без терминала |
| `TGPROXY_OUTWAY_FAMILIES` | `4`, `6` или `46`: какие семейства адресов несёт outway, если автоопределение не подходит (по умолчанию определяется по глобальным адресам и маршрутам интерфейса) |
| `TGPROXY_ROTATE` | `path`, `secret` или `all`: сменить секретный путь/секрет (при `update` и `rotate`); старая ссылка перестаёт работать |
| `TGPROXY_PURGE=1` | при `remove` удалить ещё и конфиг с секретами и скрипты |
| `TGPROXY_TELEMT_VERSION` | тег образа (по умолчанию закреплён `3.5.17`); при `update` можно указать новый |
| `TGPROXY_PUBLIC_IP` | публичный адрес IPv4 или IPv6 для `public_addr` TELEMT; по умолчанию адрес из A-, затем AAAA-записи имени прокси (см. ниже) |
| `TGPROXY_SUBNET` | подсеть `telemt` (по умолчанию свободная `172.29.x.0/24`, начиная с `172.29.77.0/24`) |
| `TGPROXY_SAVE_IMAGE`, `TGPROXY_MEM_LIMIT`, `TGPROXY_SCRIPTS_DIR`, `TGPROXY_FW` | сохранять образ (1/0), лимит памяти, каталог скриптов, `iptables` или `nft` |
| `TGPROXY_DRY_RUN=1` | команды `ip`, `iptables`, `ip6tables`, `nft`, `sysctl`, `systemctl` только печатаются, а не выполняются (остальное, включая Docker, выполняется) |

**Outway: через какой интерфейс уходит трафик к Telegram.** Выбор обязателен. Контейнер `telemt` включён в две сети: общую сеть compose (nginx и обманка) и собственную `<проект>-tgproxy` с фиксированной подсетью; маршрут по умолчанию контейнера идёт через вторую. На хосте для **этой подсети** (и только для неё) создаётся:

- таблица маршрутизации `7791` с `default via <шлюз> dev <outway>` (для `tun`/`wg`/`ppp` без шлюза: `default dev <outway>`), плюс запасной `unreachable default metric 4096`;
- правило `ip rule add from <подсеть> lookup 7791`;
- маскарад `-s <подсеть> -o <outway> -j MASQUERADE` и запрет `-s <подсеть> ! -o <outway> -j DROP` в отдельных цепочках `TGPROXY-OUTWAY` (iptables: nat и filter, фильтр подключён в `DOCKER-USER`; без iptables: отдельная таблица `nft` `tgproxy_outway`).

**IPv4, IPv6 или оба.** Outway может нести только IPv6 (типичный VPN-туннель без IPv4-адреса), только IPv4 или оба семейства. Установка определяет это по глобальным адресам интерфейса, а если адреса нет, по его маршрутам (`ip -4/-6 route show dev <outway>`), и записывает в `state.env` (`OUTWAY_FAMILIES`; `TGPROXY_OUTWAY_FAMILIES=4|6|46` переопределяет). Туннели в состоянии `UNKNOWN` (`tun`, `wg`, `ppp`) считаются рабочими. Если у outway есть IPv6, сеть `<проект>-tgproxy` создаётся двойного стека (`enable_ipv6: true`, случайная ULA-подсеть `fdXX:XXXX:XXXX:XXXX::/64`, свободная среди сетей хоста и Docker; она хранится в `state.env` как `NET_SUBNET6`), и для неё всё повторяется отдельно для IPv6: `ip -6 rule add from <подсеть> lookup 7791`, `default dev <outway>` и `unreachable default` в той же таблице, маскарад и `DROP` в `ip6tables` (или в таблице `nft` `ip6 tgproxy_outway`). Маскарад добавляется самим скриптом в свою цепочку, поэтому `ip6tables: true` в `daemon.json` не обязателен (без него цепочки `DOCKER-USER` для IPv6 нет, и правила идут в `FORWARD`; `daemon.json` не правится). Для пересылки IPv6 нужен `net.ipv6.conf.all.forwarding=1`: скрипт включает его и пишет в `/etc/sysctl.d/90-telegram-web-proxy.conf` (файл удаляется при `tgproxy-remove.sh`; если записать или включить не удалось, скрипт предупреждает). Включение пересылки отключает приём RA на интерфейсах с `accept_ra=1`, поэтому на интерфейсах с маршрутом по умолчанию из RA скрипт заранее ставит `accept_ra=2`. Семейство, которого у outway нет, для контейнера закрыто (fail-closed): при outway только с IPv6 исходящий IPv4 контейнера отбрасывается (`unreachable` и `DROP`), а в `config.toml` добавляется таблица `[network]` с `ipv6 = true` и `prefer = 6` (при обоих семействах: `ipv6 = true`, `prefer = 4`; для outway только с IPv4 таблицы нет). Контейнер получает адреса обоих семейств, а маршрут по умолчанию каждого семейства проверяется внутри контейнера (`tgproxy-config.sh status`).

Скрипт outway общий: расширение `xray-3xui` устанавливает его копию (`xray-outway.sh`) со своими именами (таблица `7792`, цепочки `XRAY-OUTWAY`, юниты `xray-3xui-outway`), и все имена берутся из `state.env` расширения (`ROUTE_TABLE`, `RULE_PRIO`, `OUTWAY_CHAIN`, `OUTWAY_NFT_TABLE`, `OUTWAY_UNIT`, `OUTWAY_SYSCTL_NAME`, ...; без них — прежние имена TELEMT, поэтому уже установленный прокси работает без изменений). Оба расширения ставятся и удаляются независимо и не трогают правила друг друга.

Остальные контейнеры, обманка, nginx и сам хост маршрутов не меняют. Примеры: `TGPROXY_OUTWAY=eth0` (трафик Telegram идёт через основной интерфейс) или `TGPROXY_OUTWAY=wg0` (через WireGuard; интерфейс `wg0` должен быть поднят, а его `AllowedIPs` должны покрывать адреса Telegram, например `0.0.0.0/0` с `Table = off`, чтобы `wg-quick` не подменял маршрут по умолчанию хоста). Сменить: меню → «change outway» или `tgproxy-config.sh outway wg0`. На вопрос об интерфейсе показывается нумерованный список (`1) ens3 ...`: состояние, адреса IPv4 и IPv6, пометка интерфейса маршрута по умолчанию), отвечать можно номером или именем; неверный ответ отклоняется, и список показывается снова.

**Публичный адрес (`public_addr`).** TELEMT использует его в параметрах внутреннего реле (адрес назначения вместе с портом 443), а не для построения ссылки, поэтому нужен всегда (в документации TELEMT поле обязательное, тип `SocketAddr`). Адрес берётся в таком порядке: `TGPROXY_PUBLIC_IP`; адрес имени прокси (A-запись, затем AAAA; `getent`, затем `dig` или `host`, если они установлены); адрес маршрута по умолчанию хоста (`ip route get 1.1.1.1`, затем `ip -6 route get 2606:4700:4700::1111`); в крайнем случае `<имя прокси>:443` (TELEMT может отвергнуть имя вместо IP). Адрес IPv6 записывается как `[адрес]:443`. Отсутствие записи в DNS — только предупреждение на этапе проверки, а не ошибка.

**Fail-closed.** Если интерфейс outway не существует или выключен, в таблице (для каждого семейства) остаётся только `unreachable`, а `DROP` не пускает трафик подсети ни через какой другой интерфейс: к Telegram контейнер не достучится, но в обход outway ничего не утечёт; `tgproxy-outway.sh status` пишет `BLOCKED (fail-closed)`. Правила переживают перезагрузку: systemd-юнит `telegram-web-proxy-outway.service` (oneshot, `RemainAfterExit`, после `docker.service`; при остановке переходит в режим «блокировать») плюс таймер `telegram-web-proxy-outway.timer`, который каждые 30 секунд восстанавливает маршруты IPv4 и IPv6 после перезапуска VPN (туннель с IPv6 тоже). Нюанс: сразу после загрузки хоста контейнер может стартовать на несколько секунд раньше юнита; в этом режиме TELEMT не открывает исходящих соединений, пока нет клиентов. Если ответы по outway теряются, проверьте строгий `rp_filter` (`net.ipv4.conf.all.rp_filter=2`): скрипт предупреждает об этом.

**Скрипты на хосте.** Установка копирует три самодостаточных скрипта (им не нужны `install.sh`, репозиторий и сеть; кроме `docker pull` образа) в `scripts/` каталога установки (`/opt/escape/scripts/`; владелец root, права 755; каталог меняется через `TGPROXY_SCRIPTS_DIR`). В копии записан путь к `state.env`, и systemd-юниты outway запускают именно их. Скрипты читают `data/telegram-web-proxy/state.env`:

- `tgproxy-config.sh`: `link`, `status`, `outway [интерфейс]` (без аргумента нумерованный список), `net-setup`, `net-check` (семейства адресов и IPv6-подсеть сети telemt), `rotate path|secret|all`, `render`, `apply` (заново собрать конфиг, подгрузить образ, применить outway и маршрут nginx: `location` или блоки `server` имени прокси, запустить контейнер), `cert` (сертификат Let's Encrypt отдельного имени прокси через сервис certbot проекта), `restart`, `pull` (`docker pull`, а при недоступности реестра `docker load` из сохранённого tar);
- `tgproxy-outway.sh`: `up`, `block`, `down`, `status`, `list` (нумерованный), `names`, `resolve`, `families`, `check`, `install-unit`, `remove-unit`; `TGPROXY_DRY_RUN=1` печатает команды обоих семейств;
- `tgproxy-remove.sh [--yes] [--purge]`: удаляет `location` или блоки `server` имени прокси (nginx перечитывается) и регистрацию его сертификата (продление прекращается), контейнер, сеть, образ, правила outway и юниты, запись в `data/extensions.compose.yml`. Остальной стек (nginx, обманка) продолжает работать. Без `--purge` конфиг, `state.env`, сохранённый образ и сертификат отдельного имени прокси остаются: переустановка даст ту же ссылку и работает офлайн; `--purge` удаляет и их, и скрипты в `scripts/` (сертификат `DOMAIN` не трогается никогда).

**Безопасность.**

- Секретный путь и секрет входят в учётные данные: ссылку нельзя публиковать. Смена пути или секрета делает старую ссылку недействительной. Секреты лежат только в `config.toml`, `state.env` (оба 600) и в ссылке, которую TELEMT печатает в свой журнал Docker (читается только root и группой `docker`).
- nginx не пишет журнал доступа для этого `location` (в нём есть токены клиента) и передаёт TELEMT `X-Forwarded-For $remote_addr` (перезапись, не добавление); TELEMT доверяет заголовку только от подсети сети compose, и порт `18080` наружу не публикуется.
- Контейнер: `read_only`, `cap_drop: ALL`, `no-new-privileges`, лимиты памяти и процессов, без API управления, без нативного слушателя MTProxy. Любые обращения к другим путям отвечает обманка.
- Адрес `fakeapp` TELEMT разрешает один раз при старте: после пересоздания только `fakeapp` перезапустите прокси (`tgproxy-config.sh restart`; `./install.sh restart` перезапускает всё сразу).
- `./install.sh remove` убирает контейнер `telemt`, но не правила outway и юниты: сначала выполните `tgproxy-remove.sh --purge` или используйте `./install.sh remove --purge`, который вызывает его (хук `ext_telegram_web_proxy_purge`) перед удалением данных.

### Панель 3x-ui (Xray) (`xray-3xui`)

Расширение `extensions.d/60-xray-3xui.sh` ставит панель [3x-ui](https://github.com/MHSanaei/3x-ui) (в образе уже есть Xray; закреплён `ghcr.io/mhsanaei/3x-ui:v3.11.0`). Настройка идёт в два этапа, оба — VLESS + REALITY с `flow=xtls-rprx-vision`:

| Этап | Inbound | Где слушает | Что видит проверяющий |
|---|---|---|---|
| 1 (установка по умолчанию) | `plain` (self-steal) | 443 хоста через TLS-фронт nginx, по **отдельному DNS-имени** (`XRAY_PLAIN_DOMAIN`, например `point.example.org`; пусто — без `plain`): соединения с этим SNI уходят в `xui:10444` (внутренний порт контейнера, не опубликован) с PROXY protocol (`sockopt.acceptProxyProtocol`) | у имени свой сертификат Let's Encrypt и server-блок nginx с сайтом-приманкой; REALITY с `serverNames=[<имя>]` и целью `nginx:443` (`xver=1`): зонд видит настоящий сайт-приманку с настоящим сертификатом |
| 2 (по желанию) | `wl` (сокрытие SNI) | тот же фронт: соединения с SNI из белого списка (`XRAY_WL_SNI`, по умолчанию `ozon.ru`, можно список через запятую) уходят в `xui:10443`; всё остальное остаётся на сайте | REALITY с `serverNames=[<SNI>]` и целью `<первое имя>:443`: настоящий TLS-ответ этого сайта |

**По умолчанию этап 1**: панель и `plain`. Этап 2 не создаётся и о нём не спрашивают, пока он не нужен (интерактивная установка спрашивает «включить inbound с SNI из белого списка? [y/N]», по умолчанию «нет»): `XRAY_ACTION=wl` (`XRAY_WL_SNI=<имя>`, `XRAY_WL=0` выключает) или `xray-config.sh wl on [SNI]` / `wl off`. Ключ состояния — `WL_ENABLED` (по умолчанию 0); установка прежней версии, где `wl` уже был, его сохраняет (`WL_ENABLED=1`). Без `wl` блок результата, ссылки, проверки (проба TLS 1.3 / h2 имени из белого списка) и `xray-remove.sh` о нём не упоминают.

**Отдельное имя `plain`.** Оно должно указывать на этот сервер (та же проверка DNS, что для `TGPROXY_DOMAIN`: предупреждение, не ошибка) и отличаться от `DOMAIN`, от имени Telegram web proxy и от SNI белого списка. Установщик запрашивает для него сертификат (`ext_cert_request`; самоподписанный, пока Let's Encrypt не выдал настоящий, таймер продления повторит попытку) и пишет server-блок (`servers.d/xray-3xui.conf`, заголовок `# cert-domain:`): порт 80 (ACME, редирект) и `listen 443 ssl proxy_protocol` с проксированием на сайт-приманку; в том же файле `set_real_ip_from` для подсети compose. Маршрут `<имя> xui:10444` добавляется в TLS-фронт через `ext_nginx_stream_put` (имя со своим сертификатом и server-блоком эта функция разрешает только расширению, которому они принадлежат). Смена: `xray-config.sh plain selfsteal ИМЯ` или `plain off` (`PLAIN_MODE` — `selfsteal` или `off`; прежний режим `direct` и опубликованный порт `PLAIN_PORT` убраны: состояние мигрирует, эти ключи удаляются).

**Панель.** Доступна по секретному пути сайта: `https://<DOMAIN>/<путь>/` (`location ^~ /<путь>/` и точный `location = /<путь>` в server сайта, `data/nginx/locations.d/xray-3xui.conf`; путь панели `webBasePath` тот же). Все остальные пути, как и раньше, обслуживает обманка. Логин `admin`, пароль и путь генерируются при установке (24 и 20 символов `A-Za-z0-9`) и хранятся только в `data/xray-3xui/state.env` (600) и базе панели `data/xray-3xui/db/` (каталог 700). Порт панели (`2053`) и порты inbound'ов (`10444`, `10443`) не публикуются: nginx ходит к ним по сети compose. В `location` панели: `proxy_http_version 1.1`, заголовки WebSocket (`Upgrade`, `Connection` через `map`), таймауты 1 час, `limit_req` (10 запросов/с, всплеск 60; зона объявлена на уровне http в `data/nginx/servers.d/xray-3xui.conf`), без журнала доступа; превышение лимита и недоступная панель отвечают обманкой (`error_page 502 503 504`), поэтому путь не выделяется. Порт, путь и пароль задаются CLI панели внутри контейнера (`x-ui setting -port -webBasePath`), пароль — через API панели (вход со стандартным `admin/admin` свежей базы, затем `setting/updateUser`), так что пароль не попадает в командную строку; CLI с паролем (`x-ui setting -username -password`) используется только как запасной вариант, если база не принимает ни сохранённые, ни стандартные данные. Подсеть сети compose добавляется в `trustedProxyCIDRs` панели, чтобы журнал входов и ограничитель попыток видели адрес клиента, а не nginx.

**Inbound'ы через API.** После запуска контейнера `xray-config.sh` входит в панель (CSRF-токен, `POST <путь>/login`) и через документированный API этой версии (`/panel/api/inbounds/list|get|add|update|del`, ключи `/panel/api/server/getNewX25519Cert`) создаёт `escape-wl` и `escape-plain` с одним клиентом в каждом (`escape-wl`, `escape-plain`). Запросы выполняет `curl` внутри контейнера (`docker exec`), JSON собирает `python3` хоста; пароль идёт только в телах запросов. Ключи REALITY (по паре на inbound), UUID клиентов и `shortId` создаются один раз и хранятся в `state.env`, поэтому повторный запуск идемпотентен: совпадающий inbound остаётся как есть (`unchanged`), отличающийся обновляется (клиенты, добавленные в панели вручную, сохраняются), дублей не бывает; `xray-config.sh inbounds --recreate` пересоздаёт их с теми же ключами (ссылки не меняются), `--new-keys` — с новыми.

**Ссылки.** `vless://<UUID>@<хост>:<порт>?type=tcp&encryption=none&security=reality&flow=xtls-rprx-vision&sni=<SNI>&fp=chrome&pbk=<открытый ключ>&sid=<shortId>&spx=%2F#<имя>`; у `plain` хост и SNI — одно и то же отдельное имя, порт 443 (`NGINX_HTTPS_PORT`); у `wl` хост — `DOMAIN` (или `XRAY_PUBLIC_HOST`), SNI — имя из белого списка. Итоговый блок установки (stdout) и `./install.sh info` печатают URL панели с логином и паролем и ссылки включённых inbound'ов (`ext_xray_3xui_result`); `xray-config.sh show` и `link` печатают то же самостоятельно.

**Проверки при установке** (фаза проверки; при отсутствии сети только предупреждения): имя `plain` (DNS-имя, не `DOMAIN`, не имя Telegram-прокси, не SNI белого списка; DNS A/AAAA указывает на этот сервер) и, только при включённом этапе 2, имена белого списка (синтаксис, не `DOMAIN` и не имена расширений, разрешение имён, AAAA если outway только IPv6, проба `openssl s_client -connect <имя>:443 -servername <имя> -tls1_3 -alpn h2`: цели REALITY нужны TLS 1.3 и h2), тег образа (`docker manifest inspect`), интерфейс outway и его семейства адресов.

**Исходящий трафик клиентов (outway).** Как у Telegram web proxy (тот же скрипт, своя копия `scripts/xray-outway.sh`): контейнер `xui` включён в общую сеть compose (nginx ↔ панель и inbound'ы) и в собственную сеть `<проект>-xray` (своя подсеть, по умолчанию свободная `172.29.200-254.0/24`, `XRAY_SUBNET`; ULA IPv6 при IPv6 у outway), маршрут по умолчанию контейнера идёт через неё (`gw_priority`, проверяется `nsenter`; иначе контейнер останавливается, fail-closed). Хост маршрутизирует эту подсеть через выбранный интерфейс: таблица `7792`, `ip rule ... priority 7792`, цепочки `XRAY-OUTWAY`, таблица `nft` `xray_outway`, юниты `xray-3xui-outway.service`/`.timer`, файлы `/etc/sysctl.d/90-xray-3xui.conf` (IPv6). Вопрос об интерфейсе по умолчанию предлагает outway Telegram web proxy, если он установлен; можно выбрать и другой. Правила обоих расширений независимы (свои таблицы, приоритеты, цепочки и юниты).

**Установка и меню.** Пункт меню «3x-ui panel» в конце `install`, либо без меню: `XRAY_PLAIN_DOMAIN=point.example.org XRAY_OUTWAY=wg0 sudo -E ./install.sh extensions --with xray-3xui`. Вопросы: отдельное имя `plain` (пусто — без него), необязательный этап 2 (по умолчанию «нет»; затем SNI белого списка), интерфейс outway. Повторный запуск на установленной системе (маркер `data/xray-3xui/installed`) открывает меню: обновить, удалить, показать учётные данные и ссылки, сменить outway, сменить пароль или путь панели, пересоздать inbound'ы, состояние, inbound с SNI из белого списка (этап 2). Без терминала:

| Переменная | Значение |
|---|---|
| `XRAY_ACTION` | `install`, `update`, `remove`, `show`, `outway`, `rotate`, `inbounds`, `wl`, `status` (по умолчанию `install`, на установленной системе `update`) |
| `XRAY_PLAIN_DOMAIN` | отдельное DNS-имя `plain` (этап 1; пусто или `off` — без него; не задано при обновлении — без изменений) |
| `XRAY_WL`, `XRAY_WL_SNI` | этап 2: `XRAY_WL=1`/`0` включает/выключает inbound `wl`; один `XRAY_WL_SNI` (`ozon.ru`; список через запятую, цель REALITY — первое имя) тоже его включает |
| `XRAY_OUTWAY`, `XRAY_OUTWAY_FAMILIES` | интерфейс outway (имя или `auto`), семейства `4`/`6`/`46` |
| `XRAY_ROTATE` | `password`, `path` или `all` |
| `XRAY_NEW_KEYS=1` | при `inbounds`: новые ключи REALITY и UUID (старые ссылки перестают работать) |
| `XRAY_PURGE=1` | при `remove`: удалить и `data/xray-3xui` (состояние, база панели, пароль, ключи) |
| `XRAY_XUI_VERSION`, `XRAY_PUBLIC_HOST`, `XRAY_SUBNET`, `XRAY_MEM_LIMIT`, `XRAY_SAVE_IMAGE`, `XRAY_SCRIPTS_DIR`, `XRAY_FW` | тег образа, хост ссылок, подсеть, лимит памяти (`192m`), сохранять образ (`docker save` в `data/xray-3xui/xui-image.tar`), каталог скриптов, `iptables`/`nft` |
| `XRAY_DRY_RUN=1` | команды outway только печатаются |

**Скрипты на хосте** (`scripts/` каталога установки, работают без репозитория, путь к `data/xray-3xui/state.env` записан в копии): `xray-config.sh` (`show`, `link [wl|plain]`, `status`, `apply`, `panel`, `inbounds [--recreate] [--new-keys]`, `plain selfsteal [ИМЯ]|off`, `wl on [ИМЯ[,ИМЯ]]|off` (`wl-sni` = `wl on`), `migrate-state`, `outway [интерфейс]`, `rotate password|path|all`, `render`, `pull`, `restart`, `net-setup`, `net-check`, `check-route`), `xray-outway.sh` (как `tgproxy-outway.sh`, переменные `XRAY_*`), `xray-remove.sh [--yes] [--purge]` (маршруты nginx, регистрация сертификата имени plain (файлы — с `--purge`), контейнер, сеть, образ, правила outway, юниты, запись compose; остальной стек работает; без `--purge` состояние и база панели остаются, переустановка вернёт ту же панель и ссылки).

**Контейнер.** `mem_limit` `192m`, `pids_limit` 256, `cap_drop: ALL` (дополнительные права не нужны: fail2ban панели выключен, `XUI_ENABLE_FAIL2BAN=false`), `no-new-privileges`, `restart: unless-stopped`, журнал json-file с `LOG_MAX_SIZE`/`LOG_MAX_FILE`, проверка здоровья ждёт, пока панель отвечает по HTTP. Данные только в bind-монтировании `data/xray-3xui/db`.

**Безопасность.** Путь и пароль панели — это её учётные данные, ссылки — учётные данные клиентов: не публикуйте их (смена: меню или `xray-config.sh rotate`). Доверие к заголовку PROXY от подсети сети compose (`set_real_ip_from` в `servers.d/xray-3xui.conf`) нужно для `plain` (REALITY передаёт адрес клиента в свою цель — nginx): туда входят только контейнеры этого стека. `./install.sh remove --purge` вызывает `xray-remove.sh --purge` (хук `ext_xray_3xui_purge`) до удаления данных.

## Каталог данных

`<каталог установки>/data/fakeapp` (или `FAKEAPP_DATA_DIR`) монтируется в контейнер **только для чтения**: приложение ничего не пишет.

| Файл | Откуда | Когда приложение видит изменения |
|---|---|---|
| `login.html` | `gen/login.py` (шаблон Go `html/template`). Обязателен: без него или с битым шаблоном приложение не стартует | после `./install.sh restart` |
| `favicon.ico` | `gen/favicon.py` (первая буква `APP_NAME`, оформление из `PAGE_SEED`) | сразу |
| любые другие файлы и подкаталоги | кладёте сами; отдаются по пути `/<путь>` | сразу |

Не отдаются:

- скрытые файлы и каталоги (`.*`);
- сам `/login.html`;
- каталоги (листинга нет).

Отсутствующий путь даёт редирект на `/`.

Права: контейнер работает от непривилегированного uid, поэтому нужны права `r` на файлах и `r-x` на каталогах (обычные 644 и 755). `install` выставляет их сам (`chmod -R a+rX`).

Новый вариант оформления:

1. Смените `PAGE_SEED` в `.env`.
2. Удалите `login.html` и `favicon.ico`.
3. Снова выполните `sudo ./install.sh install`.

## Удаление

```bash
sudo ./install.sh remove          # контейнеры, образы, таймер продления; каталог установки и данные остаются
sudo ./install.sh remove --purge  # и всё остальное
```

`remove` останавливает и удаляет контейнеры и образы и таймер продления (systemd или `/etc/cron.d/escape-certbot`). Каталог установки с `.env` и `data/` (сертификаты в том числе) остаётся, поэтому `install` возвращает ту же установку.

`remove --purge` дополнительно удаляет системные файлы расширений (Telegram web proxy и панель 3x-ui: юниты, файлы sysctl, правила файрвола и маршрутизации), данные (включая `data/letsencrypt`), **весь каталог установки** (только если в нём есть маркер `.escape-install` и это не системный путь) и указатель `/etc/escape/install-dir`, после подтверждения (`-y` его пропускает). Docker и установленные пакеты остаются. Если у Xray или 3X-UI были изменены порты ради этого стека, верните их вручную.
