# escape: личный VPN, замаскированный под обычный сайт

Скрипт разворачивает на VPS стек из 3X-UI (Xray), nginx, acme.sh и сайта-обманки. Всё работает в rootless Docker от отдельного пользователя `vpn`.

## 1. Назначение и как это выглядит снаружи

Цель: личный VPN, который для российской DPI (ТСПУ) и для активных проб выглядит как обычный сайт на вашем домене с настоящим сертификатом Let's Encrypt.

- Браузер или сканер, открывший `https://DOMAIN/`, видит правдоподобную страницу входа в веб-сервис (имя берется из `APP_NAME`).
- Порт панели наружу не опубликован. Панель, XHTTP-вход и подписки доступны только по секретным путям.
- Клиенты VPN подключаются через VLESS+REALITY на 443/tcp (основной вариант) или через VLESS+XHTTP поверх TLS (запасные варианты).

## 2. Архитектура

```
                    Интернет
                       |
   +-------------------+--------------------------+
   |                   |                          |
 TCP 443             UDP 443                    TCP 80
   |                   |                          |
   v                   v                          v
+---------------+   +----------------------------------+
| xui (Xray)    |   | nginx                            |
| VLESS+REALITY |   |  80:   ACME HTTP-01 + 301 на https|
+---+-------+---+   |  443/udp: HTTP/3 (QUIC)          |
    |       |       |  8443/tcp: TLS + PROXY protocol  |
    |       |       +----------------------------------+
    |       | не-REALITY трафик (браузер, зонд,    ^
    |       | VLESS+XHTTP+TLS) без изменений       |
    |       | + PROXY protocol -> nginx:8443 ------+
    |       v
    |   валидный клиент REALITY -> проксируется Xray
    v
 (интернет)

nginx (8443/tcp и 443/udp) маршрутизирует по пути:
   /<XHTTP_PATH>/  -> xui:10000   (XHTTP, h2c, grpc_pass)
   /<XHTTP_PATH>-<порт>/ -> xui:<порт>  (доп. входы XHTTP, порт по XHTTP_ROUTE_PORT_RE)
   /<PANEL_PATH>/  -> xui:2053    (панель 3X-UI)
   /<SUB_PATH>/    -> xui:2096    (сервер подписок 3X-UI)
   всё остальное   -> fakeapp:8080 (сайт-обманка)
```

Реальный сертификат отдает nginx. REALITY использует его как «цель» (self-steal): зонд, не прошедший проверку, получает от nginx настоящий сайт вашего домена.

| Контейнер | Образ | Роль |
|---|---|---|
| `xui` | `ghcr.io/mhsanaei/3x-ui` | 3X-UI + Xray. Публикует 443/tcp. Входы: `reality` (443) и `xhttp` (10000, только внутри сети) |
| `nginx` | `nginx:*-alpine` (с HTTP/3) | 80/tcp (ACME + редирект), 443/udp (HTTP/3), 8443/tcp (внутренний TLS с PROXY protocol). Перечитывает сертификат при его смене |
| `acme` | `neilpang/acme.sh` | Выпуск и автопродление Let's Encrypt (HTTP-01) |
| `fakeapp` | собирается из `fake-webapp/` | Сайт-обманка на Go |

Сайт-обманка (`fakeapp`): `GET /` отдает страницу входа, `POST /login` всегда отвечает 401 (со случайной задержкой), а после 3 попыток за минуту для одного логина отвечает 429. `GET /random-<RANDOM_DATA_SUFFIX>?size=N` возвращает до 500000 случайных байт. Лимит запросов действует на каждый IP (`RATE_LIMIT_RPS`/`RATE_LIMIT_BURST`), плюс общий потолок `RATE_LIMIT_GLOBAL_RPS`. Остальные пути перенаправляются на `/`.

## 3. Требования

- VPS с Ubuntu 24.04+ или Debian 12+, доступ root.
- Домен с A-записью на IP сервера (скрипт сверяет DNS и предупреждает о расхождении).
- Открытые порты: 80/tcp, 443/tcp, 443/udp.

Скрипт не настраивает файрвол. Если используете ufw (по желанию):

```bash
sudo ufw allow 80/tcp
sudo ufw allow 443/tcp
sudo ufw allow 443/udp
```

## 4. Быстрый старт

```bash
git clone https://github.com/dv-proj/escape
cd escape
sudo ./vpn.sh deploy
```

`deploy` идемпотентен. Он делает следующее:

1. Ставит пакеты, создает пользователя `vpn` (по умолчанию), включает lingering, настраивает sysctl `net.ipv4.ip_unprivileged_port_start=80` (`/etc/sysctl.d/99-vpn-rootless.conf`), ставит rootless Docker.
2. Копирует проект в `~vpn/vpn-stack` (`VPN_DIR`).
3. Создает `.env`, если его нет. Спрашивает `DOMAIN`, `ACME_EMAIL`, `APP_NAME`, `APP_DESCRIPTION`, `APP_KEYWORDS` (по умолчанию предлагается случайный правдоподобный набор, Enter принимает его), `PANEL_USERNAME`. Генерирует `PANEL_PATH`, `XHTTP_PATH`, `SUB_PATH`, `PANEL_PASSWORD`, `RANDOM_DATA_SUFFIX`, `PAGE_SEED`, `RATE_LIMIT_*`, `LOGIN_DELAY_*`, ключи REALITY, `REALITY_SHORT_ID` и `CLIENT_UUID`.
4. Создает временный самоподписанный сертификат, запускает стек и выпускает сертификат Let's Encrypt.
5. Настраивает панель, создает входы `reality` и `xhttp`, хосты ссылок и подписки.

В конце выводятся URL панели, логин, пароль, адрес `/random-<RANDOM_DATA_SUFFIX>`, три ссылки `vless://` и URL подписок. Все это можно вывести повторно командой `sudo ./vpn.sh links`. Повторный запуск обновляет файлы и перезапускает стек, секреты не пересоздаются. Существующий `$VPN_DIR/.env` используется: значения не меняются и вопросов нет, но ключи, которых в нем не хватает по сравнению с `.env.example`, дописываются в конец вместе с комментариями-описаниями (сгенерированное значение или значение по умолчанию; для каждого добавленного ключа выводится строка в лог). Пустые сгенерированные ключи заполняются на месте. Порядок, комментарии, пользовательские значения и лишние ключи не трогаются, повторный запуск ничего не меняет. `.env.example` - единственный источник описаний: у каждого ключа в нем есть комментарий.

Неинтерактивный режим:

```bash
sudo DOMAIN=app.example.com ACME_EMAIL=me@example.com APP_NAME=Notely \
  ./vpn.sh -y deploy
```

Если `DOMAIN`, `ACME_EMAIL`, `APP_NAME` (а также `APP_DESCRIPTION`, `APP_KEYWORDS`, `PANEL_USERNAME`) заданы в окружении, вопросы не задаются. Без терминала остальные вопросы получают значения по умолчанию. Флаг `-y` подтверждает все вопросы (предупреждение об ОС, несовпадение DNS, отключение запущенного rootful Docker, remove/purge). Переменные `VPN_USER` (по умолчанию `vpn`) и `VPN_DIR` позволяют изменить пользователя и каталог.

### Где что лежит (по умолчанию)

| Что | Где |
|---|---|
| Проект (рабочая копия стека) | `/home/vpn/vpn-stack` (`~vpn/vpn-stack`, `VPN_DIR`) |
| Конфигурация, пароль панели, суффикс `/random-…` | `/home/vpn/vpn-stack/.env` (права 600, читать через `sudo`) |
| БД панели 3X-UI | `/home/vpn/vpn-stack/data/xui/` |
| Сертификаты и состояние acme.sh | `/home/vpn/vpn-stack/data/certs/`, `data/acme/` |
| Страница и favicon обманки | `/home/vpn/vpn-stack/data/fakeapp/` |
| Rootless Docker пользователя `vpn` | `/home/vpn/.local/share/docker`, сокет `/run/user/<uid>/docker.sock` |

Клонированный репозиторий после `deploy` не используется: `deploy` копирует его в `VPN_DIR`. Пароль и ссылки проще всего получить командой `sudo ./vpn.sh links`.

## 5. Команды

### vpn.sh

| Команда | Права | Действие |
|---|---|---|
| `deploy` | root | Полная установка и обновление (см. выше) |
| `start` | root или `vpn` | `docker compose up -d --wait` |
| `stop` | root или `vpn` | `docker compose stop` |
| `restart` | root или `vpn` | stop + start |
| `status` | root или `vpn` | Состояние контейнеров и сертификата |
| `links` | root или `vpn` | Добавляет хосты ссылок новым входам XHTTP (`configure-hosts`), затем выводит URL панели, логин/пароль, адрес `/random-<RANDOM_DATA_SUFFIX>`, ссылки клиентов и URL подписок |
| `genkeys` | root или `vpn` | Сгенерировать и вывести приватный и публичный ключи x25519 (REALITY), UUID клиента и два Short ID. Ничего не записывает; для ручной настройки входов и клиентов в панели |
| `remove` | root | Удалить контейнеры и собранные образы |
| `remove --purge` | root | Дополнительно удалить данные, rootless Docker, пользователя и sysctl-файл |

Опции: `-y/--yes`, `--purge`, `-h/--help`.

### Вспомогательные скрипты

Обычно вызывать их вручную не нужно. Они запускаются из каталога проекта (`~vpn/vpn-stack`) от пользователя `vpn`, которому нужен доступ к его Docker-сокету. Самый простой способ:

У пользователя `vpn` оболочка `nologin`, поэтому `sudo -u vpn -i` не сработает. Запустите bash явно:

```bash
sudo -u vpn -H bash
export XDG_RUNTIME_DIR=/run/user/$(id -u)
export DOCKER_HOST=unix://$XDG_RUNTIME_DIR/docker.sock
cd ~/vpn-stack
```

Затем:

```bash
scripts/certs.sh status      # сертификат и список acme.sh
scripts/certs.sh issue       # выпуск (идемпотентно)
scripts/certs.sh renew       # принудительное продление
scripts/xui.sh links         # ссылки клиентов
scripts/xui.sh configure-panel   # логин/пароль/порт/путь панели из .env
scripts/xui.sh provision     # создать входы reality и xhttp, если их нет (и хосты ссылок)
scripts/xui.sh configure-hosts   # хосты 3X-UI: ссылки панели/подписок на DOMAIN:443, в т.ч. для новых входов XHTTP (идемпотентно)
scripts/xui.sh configure-sub     # настройки подписок в панели из .env (идемпотентно)
scripts/xui.sh sub-links     # URL подписок всех клиентов
scripts/xui.sh genkeys       # напечатать новые ключи (ничего не записывает)
```

`certs.sh` также умеет `bootstrap` (самоподписанный сертификат-заглушка). Подробности: `scripts/certs.sh help`, `scripts/xui.sh help`.

## 6. Конфигурация (.env)

Файл лежит в `$VPN_DIR/.env` (права 600). Шаблон: `.env.example`.

| Переменная | Тип | Значение по умолчанию / смысл |
|---|---|---|
| `DOMAIN` | вручную | Публичный домен |
| `ACME_EMAIL` | вручную | E-mail для Let's Encrypt |
| `ACME_SERVER` | по умолчанию | `letsencrypt` или `letsencrypt_test` (staging) |
| `APP_NAME`, `APP_DESCRIPTION`, `APP_KEYWORDS` | сгенерировано | Вид сайта-обманки. Если не заданы, `vpn.sh` подбирает согласованный случайный набор (название, описание, ключевые слова) из встроенных пулов; в интерактивном режиме он предлагается как значение по умолчанию. Значений из примера нет |
| `RANDOM_DATA_SUFFIX` | сгенерировано | Суффикс адреса случайных данных сайта-обманки (hex, 8-12 символов) |
| `PAGE_SEED` | сгенерировано | Seed страницы-приманки (32 hex-символа); из него один раз генерируется `data/fakeapp/page.html` |
| `RATE_LIMIT_RPS` | сгенерировано | Лимит запросов/с на один IP клиента (из `X-Real-IP`), случайно 8-15 |
| `RATE_LIMIT_BURST` | сгенерировано | Всплеск на один IP, случайно 15-40 |
| `RATE_LIMIT_GLOBAL_RPS` | сгенерировано | Общий потолок для всех клиентов, случайно 150-400 |
| `LOGIN_DELAY_MIN_MS`, `LOGIN_DELAY_MAX_MS` | сгенерировано | Диапазон случайной задержки ответа `POST /login`: минимум 180-400 мс, максимум = минимум + 300-900 мс |
| `NGINX_CLIENT_HEADER_TIMEOUT` | сгенерировано | `client_header_timeout` nginx на уровне `server`, секунды, случайно 20-60 |
| `NGINX_KEEPALIVE_TIMEOUT` | сгенерировано | `keepalive_timeout` nginx на уровне `server`, секунды, случайно 45-90 |
| `NGINX_HSTS_MAX_AGE` | сгенерировано | `max-age` заголовка HSTS: одно из 15552000, 31536000, 63072000 |
| `NGINX_ALTSVC_MAX_AGE` | сгенерировано | `ma` заголовка Alt-Svc: одно из 3600, 86400, 604800, 2592000 |
| `REALITY_MAX_TIME_DIFF_MS` | сгенерировано | Окно времени REALITY (`maxTimediff` в панели), мс, случайно 60000-120000. Часы клиентов должны отличаться от серверных не более чем на это значение, иначе подключение уйдет в обманку; `0` отключает проверку. Применяется только к новым входам (см. ниже) |
| `TZ` | сгенерировано | Часовой пояс контейнеров; берется с хоста при развертывании (иначе `UTC`) |
| `PANEL_PATH` | сгенерировано | Секретный путь панели |
| `PANEL_USERNAME` | вручную/`admin` | Логин панели |
| `PANEL_PASSWORD` | сгенерировано | Пароль панели |
| `PANEL_PORT` | по умолчанию | `2053` (внутри сети) |
| `SUB_PATH` | сгенерировано | Секретный путь подписок (`https://DOMAIN/SUB_PATH/<subId>`); отличается от `PANEL_PATH` и `XHTTP_PATH` |
| `SUB_PORT` | по умолчанию | `2096` (порт сервера подписок 3X-UI внутри сети, наружу не публикуется) |
| `XHTTP_PATH` | сгенерировано | Секретный путь XHTTP |
| `XHTTP_PORT` | по умолчанию | `10000` (внутри сети) |
| `NGINX_TLS_PORT` | по умолчанию | `8443` (цель REALITY, внутри сети) |
| `XHTTP_ROUTE_PORT_RE` | по умолчанию | `1[0-9]{4}` (порты 10000-19999): регулярное выражение для номера порта дополнительных входов XHTTP (см. «Дополнительные входы XHTTP»), подставляется в nginx как есть. Допустимы символы `0-9 [ ] - { } , \| ( ) ?`; выражение должно совпадать только с портами 1024-65535 и не совпадать с `PANEL_PORT`, `SUB_PORT`, `NGINX_TLS_PORT`, иначе nginx не запустится. Изменение: `vpn.sh restart` |
| `REALITY_PRIVATE_KEY`, `REALITY_PUBLIC_KEY` | сгенерировано | Ключи x25519 |
| `REALITY_SHORT_ID` | сгенерировано | 8-16 hex-символов |
| `CLIENT_UUID` | сгенерировано | UUID клиента (общий для обоих входов) |
| `DATA_DIR` | по умолчанию | `./data` (БД панели, сертификаты, состояние acme.sh) |
| `XUI_DB_JOURNAL_MODE` | по умолчанию | `DELETE`: БД панели целиком в `data/xui/x-ui.db`, без `-wal`/`-shm` (проще бэкап). `WAL` — режим 3X-UI по умолчанию. Применяется при перезапуске `xui` (`vpn.sh restart`) |
| `DOCKER_SUBNET` | по умолчанию | `172.30.53.0/24`; nginx доверяет PROXY protocol только из этой подсети |
| `XUI_IMAGE`, `NGINX_IMAGE`, `ACME_IMAGE` | по умолчанию | Закрепленные версии образов |

Как менять значения после установки: отредактируйте `$VPN_DIR/.env` (не файл в клонированном репозитории, повторный `deploy` его не использует, если `.env` в `VPN_DIR` уже есть), затем:

- Данные сайта-обманки (`APP_*`, `TZ`) и пути/порты nginx: `vpn.sh restart` (контейнеры пересоздаются по `docker compose up`).
- Логин, пароль или путь панели: `scripts/xui.sh configure-panel` (он сам перезапускает xui), затем `vpn.sh restart`, чтобы nginx получил новый `PANEL_PATH`.
- `SUB_PATH`, `SUB_PORT`: `scripts/xui.sh configure-sub` (применяет настройки в панели и перезапускает xui, если что-то изменилось), затем `vpn.sh restart`, чтобы nginx получил новые значения.
- `XHTTP_PATH`: исправьте путь во входе `xhttp` в панели и перезапустите стек. Клиентам нужны новые ссылки.
- `REALITY_MAX_TIME_DIFF_MS`: используется только при создании входа `reality`. В существующих установках откройте вход `reality` в панели и задайте «Max Time Diff (ms)» (значение из `.env`) либо удалите входы и запустите `scripts/xui.sh provision`. Автоматической миграции нет. При обновлении `vpn.sh` дописывает недостающие ключи в `.env` сам.
- Ключи REALITY, `REALITY_SHORT_ID`, `CLIENT_UUID`: `provision` не меняет существующие входы (создает их, только если нет входов с такими именами). Обновите значения в панели вручную или удалите входы `reality`/`xhttp` и запустите `scripts/xui.sh provision`. Клиенты должны получить новые ссылки (`vpn.sh links`).

### Страница-приманка

Страница входа сайта-обманки не шаблонная: разметка, CSS, имена классов и id, порядок тегов, тексты и необязательные элементы (ссылка «Forgot password?», «Remember me», подвал) выбираются детерминированно из `PAGE_SEED`, поэтому у разных развертываний HTML разный. При первом запуске `fakeapp` записывает результат в `$VPN_DIR/data/fakeapp/page.html` (обычный Go `html/template`, его можно править) и дальше читает этот файл.

- Файл принадлежит пользователю контейнера (uid 65532, каталог с правами 700), поэтому с хоста его правят через одноразовый контейнер с образом `ACME_IMAGE` (команды от пользователя `vpn`, как в разделе «Вспомогательные скрипты», из `~/vpn-stack`):

  ```bash
  IMG=neilpang/acme.sh:3.1.6   # значение ACME_IMAGE из .env
  docker run --rm --network none -v "$PWD/data/fakeapp:/d" --entrypoint cat $IMG /d/page.html > page.html
  nano page.html
  docker run --rm -i --network none -v "$PWD/data/fakeapp:/d" --entrypoint /bin/sh $IMG -c 'cat > /d/page.html' < page.html
  docker compose restart fakeapp
  ```

- Если файл не разбирается как шаблон, в логе `fakeapp` будет ошибка, а страница отдается сгенерированная (файл не перезаписывается).
- Чтобы заново сгенерировать страницу из `PAGE_SEED`, удалите файл (`docker run --rm -v "$PWD/data/fakeapp:/d" --entrypoint rm $IMG -f /d/page.html`) и выполните `docker compose restart fakeapp`.
- Для другого варианта измените `PAGE_SEED` в `.env` (любые 16-64 символа `0-9a-f`), удалите файл и выполните `vpn.sh restart`.
- Лимиты: вместо общего rate-limiter 10 RPS из ТЗ по просьбе заказчика сделан лимит на каждый IP (token bucket, `RATE_LIMIT_RPS`/`RATE_LIMIT_BURST`) плюс общий потолок `RATE_LIMIT_GLOBAL_RPS`, чтобы один клиент не мог «выключить» сайт для всех. Превышение дает 429 со страницей в том же стиле и `Retry-After`.
- Задержка входа: `POST /login` отвечает (401 и 429) не сразу, а через случайное время из диапазона `LOGIN_DELAY_MIN_MS`..`LOGIN_DELAY_MAX_MS` (логнормальное распределение, не равномерное).
- Заголовки (CSP, `Referrer-Policy`, nonce, `Permissions-Policy`, `Cache-Control` и т. п.) различаются между развертываниями и детерминированно выводятся из `PAGE_SEED`.
- Favicon: `/favicon.ico` отдает встроенную пустую прозрачную иконку 16x16. Чтобы заменить ее, положите свой файл как `$VPN_DIR/data/fakeapp/favicon.ico` (тем же способом, что и `page.html`, через одноразовый контейнер: `docker run --rm -i --network none -v "$PWD/data/fakeapp:/d" --entrypoint /bin/sh $IMG -c 'cat > /d/favicon.ico' < favicon.ico`) и выполните `docker compose restart fakeapp` (файл читается при старте; до 1 МБ). `/robots.txt` и `/sitemap.xml` по-прежнему перенаправляют на `/`.
- Данные шаблона: `.AppName`, `.Description`, `.Keywords`, `.BaseURL`, `.JSONLD`, `.Nonce` (обязателен в `<style>`/`<script>` из-за CSP), `.Time`, `.UnixMilli`, `.OffsetSec`, `.Year`, `.HideForm` и `.State` (`""`, `"invalid"` для 401, `"throttled"` для 429). Поля формы `username`/`password` и `action="/login"` менять не нужно.

## 7. Варианты использования

Все три ссылки печатаются командой `./vpn.sh links` (или `scripts/xui.sh links`). Один и тот же `CLIENT_UUID` работает на обоих входах.

### A) VLESS + REALITY (Vision): основной

Когда использовать: по умолчанию, это самый быстрый и устойчивый вариант. Работает по TCP 443.

Формат ссылки:

```
vless://UUID@DOMAIN:443?encryption=none&security=reality&sni=DOMAIN&fp=chrome&pbk=PUBLIC_KEY&sid=SHORT_ID&spx=%2F&type=tcp&flow=xtls-rprx-vision#имя
```

Поля клиента:

| Поле | Значение |
|---|---|
| Address | `DOMAIN` |
| Port | `443` |
| UUID | `CLIENT_UUID` |
| Flow | `xtls-rprx-vision` |
| Security | `reality` |
| SNI | `DOMAIN` |
| Fingerprint | `chrome` |
| Public key | `REALITY_PUBLIC_KEY` |
| Short ID | `REALITY_SHORT_ID` |
| SpiderX | `/` |
| Network | `tcp` |

Почему устойчив к активным пробам: схема self-steal. Целью REALITY служит собственный nginx с настоящим сертификатом вашего домена (`xver=1`, PROXY protocol). Любой, кто не знает ключ и short id (браузер, сканер), получает от nginx настоящий TLS с настоящим сертификатом и видит сайт-обманку, а не чужой домен с подозрительными расхождениями.

### B) VLESS + XHTTP поверх TLS (h2) через nginx: запасной

Когда использовать: если REALITY блокируется или замедляется. Клиент подключается к 443/tcp как обычный TLS-клиент, Xray передает такое соединение на nginx, а nginx по секретному пути отправляет его в XHTTP-вход.

```
vless://UUID@DOMAIN:443?encryption=none&security=tls&sni=DOMAIN&alpn=h2&fp=chrome&type=xhttp&host=DOMAIN&path=%2FXHTTP_PATH%2F&mode=auto#имя-xhttp
```

Поля: Security `tls`, SNI `DOMAIN`, ALPN `h2`, Network `xhttp`, Host `DOMAIN`, Path `/XHTTP_PATH/` (см. точную строку в `links`), Mode `auto`, Flow пустой. Нужен настоящий сертификат Let's Encrypt: в Xray 26 убран `allowInsecure`, а самоподписанный сертификат-заглушка клиент отвергнет. Поэтому дождитесь успешного выпуска сертификата.

### C) VLESS + XHTTP поверх HTTP/3 (QUIC, UDP 443)

Когда использовать: если UDP на 443 не режется. Ссылка отличается от B значением `alpn=h3`:

```
vless://UUID@DOMAIN:443?encryption=none&security=tls&sni=DOMAIN&alpn=h3&fp=chrome&type=xhttp&host=DOMAIN&path=%2FXHTTP_PATH%2F&mode=auto#имя-xhttp-h3
```

Трафик идет по UDP 443 прямо в nginx, минуя REALITY. Оговорка: в России QUIC часто ограничивают или режут, поэтому это опция, а не основной вариант. Нужен клиент с поддержкой XHTTP поверх QUIC.

### D) XHTTP через CDN (например, Cloudflare): вручную, для продвинутых

Скрипты это не настраивают. Идея: DNS-запись домена идет через CDN в режиме proxy, CDN принимает HTTPS от клиента и пересылает запросы на ваш nginx (443, путь `/XHTTP_PATH/`), откуда они попадают в XHTTP-вход. IP сервера при этом скрыт.

Ограничения:

- REALITY на 443/tcp конфликтует с хостом, проксируемым CDN, для того же домена: CDN подключится к Xray на 443 и не пройдет проверку REALITY. Рекомендуется отдельный поддомен для CDN, который идет в том же стеке (нужно добавить его в `server_name` и в сертификат).
- CDN должен поддерживать стриминг (HTTP/2 к origin, gRPC) либо используйте режим `packet-up`, который работает через обычные запросы. В `auto` поведение зависит от клиента, `packet-up` задается на клиенте и сервере.
- Эта схема в репозитории не проверена и требует ручной настройки DNS, сертификата для поддомена, `server_name` в nginx и ссылки клиента.

### Результаты проверки из России (ноябрь 2026)

Проверка через мобильную сеть РФ на рабочем сервере:

- Сайт-обманка и `/random-…` (500 КБ) открываются, подписка отдается (200).
- B) XHTTP + TLS (h2) с ссылками из `links`/подписки: работает (5 МБ, около 2.8 МБ/с).
- A) REALITY (Vision): рукопожатие проходит, но после нескольких килобайт передача замирает. Это поведение ТСПУ по протоколу, а не блокировка IP: тот же IP по обычному TLS работает.

Поэтому в этой сети используйте вариант B (или подписку, где он есть). Результат зависит от оператора и региона и может меняться.

### Сравнение

| Вариант | Устойчивость к DPI | Скорость | Нужен UDP | Нужен сертификат | Можно за CDN |
|---|---|---|---|---|---|
| A) REALITY (Vision) | высокая в теории; в мобильной сети РФ замирает (см. выше) | высокая | нет | есть (self-steal) | нет |
| B) XHTTP + TLS (h2) | средняя/высокая | средняя | нет | да, настоящий | да (см. D) |
| C) XHTTP + HTTP/3 | зависит от QUIC | высокая при отсутствии потерь | да | да, настоящий | нет |
| D) XHTTP через CDN | средняя (зависит от CDN) | средняя | нет | да | да |

### Клиенты

Нужны версии с поддержкой REALITY и XHTTP (свежие релизы):

- Windows/Linux/macOS: v2rayN, NekoBox.
- Android: v2rayNG, NekoBox, Hiddify.
- iOS/macOS: Streisand, FoXray, Shadowrocket, Hiddify.

Импорт: скопируйте `vless://` из `./vpn.sh links` и вставьте из буфера обмена в клиент. QR-код можно получить в панели (кнопка у клиента во входе).

### Подписки

Подписка отдает клиентскому приложению сразу все ссылки пользователя (REALITY, XHTTP h2, XHTTP h3) одним адресом, и приложение обновляет их само:

```
https://DOMAIN/SUB_PATH/<subId>
```

`./vpn.sh links` (или `scripts/xui.sh sub-links`) печатает URL подписки каждого клиента. В приложении добавьте его как подписку (v2rayNG, Hiddify, Streisand, v2rayN и др.). `subId` задается у клиента в панели (поле «Subscription»); при создании входов `deploy` дает обоим стартовым клиентам один `subId`, поэтому у них один URL с тремя ссылками. В установках, созданных до появления подписок, у стартовых клиентов разные `subId` (будет два URL): чтобы получить один, задайте обоим клиентам в панели одинаковый `subId`.

Как это устроено:

- Сервер подписок 3X-UI слушает `SUB_PORT` внутри контейнера `xui` (наружу не публикуется), nginx проксирует `https://DOMAIN/SUB_PATH/` на него без изменения пути и не пишет такие запросы в access-лог (в URL лежит секретный `subId`). TLS терминирует nginx.
- `scripts/xui.sh configure-sub` (вызывается из `deploy`) через API панели задает `subEnable`, `subPort`, `subPath=/SUB_PATH/`, `subDomain=DOMAIN`, `subURI=https://DOMAIN/SUB_PATH/` и отключает TLS самого сервера подписок. Повторный запуск ничего не меняет, если настройки уже верны. Шаблон названий ссылок дополняется токеном `{{HOST}}` (чтобы ссылки h2 и h3 различались), только если он остался заводским.
- Хосты 3X-UI (`scripts/xui.sh configure-hosts`, вызывается из `provision`): без них панель и подписки строят ссылки из самого входа, то есть для `xhttp` с внутренним портом 10000 и `security=none` (TLS на деле терминирует nginx на 443), и такие ссылки не работают. Хосты `h2` и `h3` входа `xhttp` задают `DOMAIN:443`, TLS, SNI и Host `DOMAIN`, `alpn` `h2`/`h3`, fingerprint `chrome`; хост `tcp` входа `reality` задает `DOMAIN:443` с сохранением параметров REALITY. Пока у входа есть хосты, его собственная ссылка заменяется ссылками хостов (не дублируется). Поэтому ссылки и QR из панели теперь совпадают с `scripts/xui.sh links`. Хосты можно править в панели (раздел Hosts): скрипт сравнивает только свои поля.
- Клиентам, созданным вручную, задайте тот же `subId`, чтобы объединить их ссылки в одну подписку.

### Новые ключи для ручной настройки

```bash
sudo ./vpn.sh genkeys
```

Выводит приватный и публичный ключи x25519, UUID и два Short ID (по 8-16 hex-символов, разные). В панели: во входе REALITY поля Private Key и Public Key, в Short IDs оба значения через запятую; UUID идет в поле ID клиента. Значения из `.env` команда не меняет: существующие входы и ссылки остаются прежними.

### Дополнительные пользователи

В панели 3X-UI откройте вход `reality` и `xhttp`, добавьте клиентов. Электронная почта (email) клиента должна быть уникальной в пределах панели, один и тот же человек может иметь по клиенту на каждом входе с разными email. Ссылки и QR берутся из панели. Для REALITY-клиентам задайте Flow `xtls-rprx-vision`. Чтобы у человека была одна подписка со всеми ссылками, задайте клиентам на обоих входах одинаковый `subId` (его URL: `https://DOMAIN/SUB_PATH/<subId>`).

### Дополнительные входы XHTTP

Новый вход XHTTP (например, с другими `xPaddingBytes`, `mode` или своим набором клиентов) создается только в панели, без правки nginx. nginx направляет `https://DOMAIN/<XHTTP_PATH>-<порт>/` на `xui:<порт>` для любого порта, совпадающего с `XHTTP_ROUTE_PORT_RE` (по умолчанию `1[0-9]{4}`, то есть 10000-19999).

Правила для входа (Inbounds → Add Inbound):

| Поле | Значение |
|---|---|
| Protocol | `vless` |
| Listen IP | пусто |
| Port | свободный порт, подходящий под `XHTTP_ROUTE_PORT_RE`, кроме `XHTTP_PORT` (10000), например `10001` |
| Transmission | `XHTTP` |
| Path | `/<XHTTP_PATH>-<порт>/`, например `/3xo28djspgt9c3y6gwi3j3-10001/` (`XHTTP_PATH` из `.env`, номер порта должен совпадать с полем Port) |
| Host | пусто |
| Security | `none` (TLS снимает nginx) |
| Sockopt → Trusted X-Forwarded-For | `X-Real-IP` (по желанию: тогда в журнале Xray видны реальные IP) |
| Клиенты | Flow пустой; `subId` как у других клиентов человека, если нужна одна подписка |

Сохраните вход. В течение минуты таймер `vpn-hosts.timer` (systemd пользователя `vpn`, ставится `deploy`) добавит ему хосты `h2` и `h3` (`DOMAIN:443`, TLS, SNI и Host `DOMAIN`, fingerprint `chrome`). После этого ссылки и QR в панели и подписка рабочие: обновите страницу панели или подписку в приложении. Сразу, без ожидания: `sudo ./vpn.sh links`. Перезапуск nginx или xui не нужен.

Пока хостов нет (первую минуту), панель показывает ссылку с внутренним портом (например, `:10001`) и `security=none`; такую ссылку клиент не примет, ее не нужно использовать.

- Проверить таймер: `sudo -u vpn XDG_RUNTIME_DIR=/run/user/$(id -u vpn) systemctl --user list-timers vpn-hosts.timer`, журнал: `sudo -u vpn XDG_RUNTIME_DIR=/run/user/$(id -u vpn) journalctl --user -u vpn-hosts`. Таймер только добавляет недостающие хосты и ничего не меняет, пока стек остановлен; `vpn.sh remove` его отключает, повторный `deploy` включает.
- Хосты добавляются только входу, у которого их еще нет. Если вы изменили или добавили хосты такого входа вручную, скрипт их не трогает.
- Если путь не совпадает с `/<XHTTP_PATH>-<порт>/` или Security не `none`, скрипт выведет предупреждение и хосты не создаст: такой вход nginx не обслуживает (запросы уходят на сайт-обманку).
- Порт, не подходящий под `XHTTP_ROUTE_PORT_RE`, nginx не маршрутизирует: такой путь обрабатывается как любой неизвестный адрес (ответ сайта-обманки), поэтому, например, `/<XHTTP_PATH>-2053/` не ведет к панели и ничем не отличается от `/foo`. Наружу порты входов не публикуются, клиенты всегда подключаются к 443.
- Входы на 443/tcp (REALITY) создавать нельзя: порт уже занят входом `reality`.

## 8. Панель 3X-UI

- URL: `https://DOMAIN/PANEL_PATH/`.
- Логин и пароль: `PANEL_USERNAME` / `PANEL_PASSWORD` в `.env`; также выводятся `vpn.sh links`.
- Подписки и хосты (ссылки с `DOMAIN:443`) настраиваются скриптом, см. раздел «Подписки»; не отключайте хосты `h2`/`h3`/`tcp`, иначе ссылки панели снова получат внутренний порт. Если подписки не открываются: `scripts/xui.sh configure-sub`.
- Не меняйте порты и target входов без необходимости: порты 10000 и 8443 связаны с настройкой nginx, а target REALITY должен указывать на `nginx:8443` с `xver=1`.
- Не публикуйте адрес панели и не передавайте путь третьим лицам.

## 9. Сертификаты

- Выпуск происходит автоматически при `deploy` (HTTP-01 на порту 80, DNS должен указывать на сервер).
- Продление автоматическое: контейнер `acme` запускает cron acme.sh, nginx сам перечитывает сертификат при смене файлов.
- Проверка: `./vpn.sh status` или `scripts/certs.sh status`.
- Для пробных запусков без лимитов Let's Encrypt поставьте в `.env` `ACME_SERVER=letsencrypt_test` (staging, сертификат не доверенный, клиенты в режиме TLS его не примут). Для рабочей схемы верните `letsencrypt` и выполните `scripts/certs.sh issue`/`renew`.

## 10. Безопасность и маскировка

- Не делитесь путем панели и XHTTP, а также паролем и ссылками.
- Выберите правдоподобные `APP_NAME`, `APP_DESCRIPTION`, `APP_KEYWORDS`.
- Rootless Docker: контейнеры работают от непривилегированного `vpn`; у контейнеров сброшены capabilities и включен `no-new-privileges`.
- Порт панели не опубликован, наружу торчит только 80, 443/tcp и 443/udp.
- Встроенный fail2ban в 3X-UI отключен (нет iptables/NET_ADMIN). Защита от перебора на сайте-обманке и лимит запросов реализованы в самом `fakeapp`.
- Логи: `json-file`, ротация 10 МБ x 3 на контейнер. Лог доступа к путям XHTTP и подписок в nginx отключен.
- Анализ признаков, по которым развертывание можно распознать, и статус исправлений: [docs/DETECTION.md](docs/DETECTION.md).

### Выбор имени домена и защита nginx

- Выбирайте нейтральное имя (`app.example.com`, `docs.<ваш-домен>`): оно видно в SNI и в журналах CT. Избегайте слов `vpn`, `proxy`, `xray`, `tunnel`, `wg` и подобных в любой части имени; `vpn.sh` предупредит и спросит, продолжать ли (с `-y` продолжит; без терминала только предупредит).
- nginx не выдает абсолютных редиректов с внутренним портом (`absolute_redirect off`): `/PANEL_PATH` и `/XHTTP_PATH` без слеша редиректятся относительно.
- На уровне `server` стоят короткие таймауты со случайными значениями около стандартных; долгие таймауты (5 мин) действуют только в `location` XHTTP. `max-age` HSTS и `ma` Alt-Svc тоже выбираются случайно при развертывании.

### Резервная копия

Отдельной команды бэкапа нет. Скопируйте от root, лучше при остановленном стеке (`sudo ./vpn.sh stop`):

```bash
sudo tar -C /home/vpn/vpn-stack -czf /root/vpn-backup-$(date +%Y%m%d).tar.gz .env data/xui data/certs data/acme data/fakeapp
sudo ./vpn.sh start
```

По умолчанию `XUI_DB_JOURNAL_MODE=DELETE`, и вся БД панели лежит в `x-ui.db`. Каталог `data/xui` всё равно копируйте целиком: при `XUI_DB_JOURNAL_MODE=WAL` рядом с `x-ui.db` лежат `x-ui.db-wal` и `x-ui.db-shm`, и часть данных находится в них. В режиме `DELETE` все данные лежат в одном `x-ui.db`. Восстановление: распакуйте архив в `VPN_DIR` на новом сервере после `deploy` (с тем же `DOMAIN`) и выполните `sudo ./vpn.sh restart`.

## 11. Удаление

```bash
sudo ./vpn.sh remove          # контейнеры и образы; данные, пользователь и Docker остаются
sudo ./vpn.sh remove --purge  # + данные (сертификаты, БД панели), rootless Docker, пользователь vpn, sysctl-файл
```

Установленные пакеты не удаляются никогда. Текущее значение sysctl сохраняется до перезагрузки.

## 12. Диагностика и FAQ

Логи (от пользователя `vpn`, в каталоге проекта; см. раздел 5 про окружение):

```bash
docker compose ps
docker compose logs --tail=100 nginx
docker compose logs --tail=100 xui acme fakeapp
```

- Сертификат не выпускается: проверьте A-запись домена, что 80/tcp доступен снаружи (файрвол провайдера и ufw), и что nginx запущен. Затем `scripts/certs.sh issue`. Для отладки используйте staging.
- После `remove --purge` и новой установки ничего не подключается: при новой установке генерируются новые ключи REALITY, `CLIENT_UUID`, `XHTTP_PATH` и `SUB_PATH`, поэтому старые ссылки и подписки недействительны. Удалите их в приложении и добавьте заново из `sudo ./vpn.sh links`.
- REALITY подключается, но данные перестают идти после нескольких килобайт: так ведет себя ТСПУ в части сетей РФ (см. «Результаты проверки из России»). Переключитесь на XHTTP (B).
- XHTTP не передает данные или ссылки из панели содержат порт `10000`: ссылки построены без хостов. Выполните `scripts/xui.sh configure-hosts` и возьмите ссылки заново (`vpn.sh links` или подписка).
- Приложение пишет о таймауте при добавлении подписки: проверьте, что URL имеет вид `https://DOMAIN/SUB_PATH/<subId>` (`vpn.sh links`), и выполните `scripts/xui.sh configure-sub`, затем `vpn.sh restart`.
- Клиент не подключается: проверьте синхронизацию времени на сервере и клиенте (REALITY и TLS чувствительны), `fingerprint`, `shortId`, публичный ключ, SNI равен `DOMAIN`, Flow `xtls-rprx-vision` только для REALITY. Для вариантов B и C нужен действительный сертификат.
- Проверка маскировки: `curl -I https://DOMAIN/` должен вернуть страницу сайта-обманки (200), `curl -I http://DOMAIN/` вернет 301 на https.
- Реальные IP клиентов: в nginx приходят через PROXY protocol (TCP) и напрямую (QUIC). При rootless Docker источник соединения на хосте может отображаться как адрес внутренней сети, поэтому не полагайтесь на IP в логах контейнеров как на абсолютно точный.
